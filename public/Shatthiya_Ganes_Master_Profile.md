**06/2025 – 01/2026** Tech stack: Flutter, Laravel, FVM, Provider, Riverpod, Laravel Sanctum, GitLab, Postman, Laravel Scramble (API docs), Oracle, Docker, Nginx

&nbsp;

Integrated mobile application for Universiti Malaysia Pahang Al-Sultan Abdullah (UMPSA), centralizing hostel registration, semester payments, course applications, exam results, leave applications, financial info, attendance, calendar, notifications, and e-wallet into a single platform for 20,000+ university users. Mobile app built in Flutter with a Laravel API/web-admin backend, integrated with UMPSA's internal SSO.

&nbsp;

- Designed the entire backend architecture personally as a set of independent Laravel microservices split by domain rather than one monolithic application: a General/Corporate API service (data umum, korporat, PTj — events, announcements, common/reference data) as the first repo built, with Student, Academic, Finance, and HR services following the same pattern.  
- Challenge: the platform's features were initially prone to cross-feature failures because they shared a single data access layer — a bug or slowdown in one feature (e.g. payment processing) risked affecting unrelated features (e.g. course applications). Solution: separated each domain into its own service boundary with its own data access layer and API contract, cutting cross-feature regressions and allowing each module to be optimized and deployed on its own schedule.  
- Built a shared set of conventions reused across every microservice: versioned routing (`/api/v1/{module}/...`, e.g. `/api/v1/student/lejar/invoices`), a custom Sanctum setup mapping personal access tokens to an Oracle `WEBAPP_TOKENS` table instead of Laravel's default token store, per-user/IP API rate limiting (60 requests/minute via `RateLimiter`), and a `ForceJsonRequestHeader` middleware so every endpoint — including validation and error responses — always returns JSON rather than HTML, keeping mobile-side error handling consistent.  
- Designed an `OptionalSanctumAuth` middleware (`auth.optional`) to support guest-vs-authenticated endpoints with role-based data filtering in a single codepath: it resolves the bearer token (if any) into a `PUBLIC`, `STUDENT`, or `STAFF` role and injects `auth_user` / `auth_role` / `auth_user_type` into the request, so one endpoint (e.g. calendar, events, announcements) can serve public visitors, logged-in students, and staff with different data visibility without duplicating routes or controllers.  
- Standardized all API responses through a shared `ApiResponse` trait (success/error/validationError/unauthorized/forbidden/notFound/paginated/etc.) and centralized error mapping through an `ApiException` class plus a global exception `Handler`, so every microservice returns a consistent JSON contract (`status`, `message`, `data`, `pagination`) and consistent HTTP status codes for auth, validation, not-found, throttling, and database errors.  
- Worked across multiple Oracle database schemas/connections in the same Laravel project (`CMSADMIN` for student/staff/financial records, `UMP_DEV` for general UMP data, `ASIS` for staff info), building models against schema-qualified tables and using Form Request classes plus API Resource transformers to validate input and shape outgoing JSON without leaking raw Oracle column names to the frontend.  
- Containerized each microservice with Docker Compose (PHP-FPM app container \+ Nginx webserver container) for local development, and owned deployment to a staging environment (SSH into the server, `git pull`, `php artisan optimize` inside the container) verified against Laravel Scramble-generated API docs before handoff to the mobile frontend team.  
- Wrote the team's onboarding/handover documentation for the backend (architecture overview, middleware, routing conventions, controller/Resource/Request patterns, Docker setup, deployment steps) so new developers unfamiliar with Laravel APIs or microservices could ramp up independently.  
- Structured and documented the Laravel Web Admin panel as its own set of modules — Login, Profile, Dashboard, Notifikasi, Tetapan (Settings), Tetapan Modul, Menu Aplikasi, Hyperlink, and Widget — with each module's function, code location, and related API endpoints documented for handover, mirroring the same modular philosophy as the backend microservices.  
- Student-facing scope confirmed in the Business Requirements Specification: students use the app to view general university information, pay tuition/fees (yuran) and view saman/fines, check up-to-date academic information, and view exam schedules/results and related student activities — matching the exam results, financial info, and calendar features listed above.
